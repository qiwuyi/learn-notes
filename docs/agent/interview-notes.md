## 一、执行、上下文与协作

本组 Q1–Q4 来源：[随波逐牛的字节 AI Agent 实习面经](https://www.nowcoder.com/feed/main/detail/8a553bb6ea8445d0b0abe11e87614cea?sourceSSR=%E5%85%B6%E4%BB%96)。

### Q1：边执行边决策与先规划再执行，各适合怎样的任务？

考察点：ReAct、Plan-and-Execute、动态反馈。

::: details 展开学习版参考答案与练习
ReAct 将决策、行动和环境反馈交替组织，适合需要试探的任务，例如先查看报错，再选择要读的文件。Plan-and-Execute 先拆出子任务再执行，适合目标明确、依赖较多的任务，例如分模块迁移接口。后者也可以根据执行结果重新规划，两者不是互斥开关。[ReAct 论文](https://arxiv.org/abs/2210.03629)

回答时还要交代成本：每一步都重新决策可能增加调用次数；计划过细则可能在环境变化后失效。可以先制定粗计划，在子任务内部使用反馈循环，并限制重规划次数。

**练习：** 为「修复一个失败测试」分别画出两种执行流程，标明什么时候读取新证据、什么时候调整计划。
:::

### Q2：压缩长对话时，如何保住用户的关键要求？

考察点：上下文预算、结构化状态、摘要失真。

::: details 展开学习版参考答案与练习
把任务目标、硬约束、已确认决策、未完成事项作为明确字段保存，再压缩较旧的讨论和可重新获取的工具输出。摘要应保留证据位置，让后续步骤能回查原文；不能默认压缩后的文本与原始记录等价。上下文整理、摘要和按需检索可结合使用。[上下文工程说明](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)

例如用户要求「只修改 dev 配置」，这条约束应进入执行前校验，不能仅依赖模型记忆。用包含多轮纠正的样本检查压缩后约束是否还在、是否被误写。长期记忆与当前会话状态也应分开管理。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

**练习：** 写一段十轮对话，其中两次修改需求。压缩后逐项核对最终要求，特别检查被撤销的旧要求。
:::

### Q3：工具数量多、返回结果长，怎样控制上下文占用？

考察点：工具发现、返回契约、Token 预算。

::: details 展开学习版参考答案与练习
先按任务和权限筛选候选工具，只向模型提供当前需要的工具定义。返回值优先使用结构化字段、分页和可追溯的结果引用；长日志先查询时间段和错误类型，再按需展开。不要把整份日志默认塞进提示词。

需要区分「压缩」和「丢弃」：截断可能丢掉最后的错误，摘要可能遗漏关键标识。工具返回应说明结果总数、是否截断和后续获取方式。分别记录工具定义、历史消息和工具结果占用的 Token，再定位主要开销。

**练习：** 设计一个日志查询工具的返回结构，包含摘要、分页标记和原始记录引用；说明下一次如何查询遗漏部分。
:::

### Q4：多个 Agent 共同编辑文件时，如何协调并发修改？

考察点：任务边界、隔离、版本冲突。

::: details 展开学习版参考答案与练习
先按文件或模块划分所有权，让子 Agent 在独立工作区生成补丁，由协调者统一集成。独立工作区隔离了写入，但不会自动解决合并冲突；提交补丁时还要记录基线版本，基线变化后重新检查补丁。

若必须操作共享文件，可以采用串行写入或带版本检查的乐观并发控制。仅靠提示词约定「不要覆盖别人」不够。即使 Git 合并成功，也要检查接口、配置和业务语义是否一致，最后验证集成结果。

**练习：** 两个 Agent 都读取版本 v1，一个修改函数签名，一个修改调用方。写出怎样发现过期基线、怎样合并和验证。
:::

## 二、检索、证据与终止条件

本组 Q5–Q8 来源：[智能求职不迷路的字节多模态算法实习面经](https://www.nowcoder.com/feed/main/detail/2a15c4bfdf7e4c0a91ec1b1fde2970b1)。

### Q5：依据什么决定停止查资料、开始形成答案？

考察点：完成条件、证据覆盖、资源预算。

::: details 展开学习版参考答案与练习
先把任务拆成必须回答的要点，检查每个要点是否有可用证据、是否存在未解决冲突。完成判断还应结合工具执行结果，例如查订单需要拿到匹配的订单标识和状态，不能只看模型说「我找到了」。

另设最大步数、总耗时和费用限制。达到预算只代表被迫停止，不代表任务成功；应明确返回已确认结论、缺失信息和下一步建议。对无法从现有资料确定的问题，保留不确定性。

**练习：** 为「查询一笔订单的退款进度」列出完成、需要补充信息、失败三种退出条件。
:::

### Q6：Agent 持续循环却没有进展时，如何发现并终止？

考察点：进展检测、重试策略、执行状态。

::: details 展开学习版参考答案与练习
观察近期的工具名、规范化参数、返回状态和新获得的证据。如果不断重复相同请求，且没有新增信息或状态推进，就应触发停滞处理。循环次数上限是最后的兜底，不能替代诊断。

按错误类型处理：临时故障采用有上限的退避重试；参数错误先校验或补全；权限不足停止并说明；路线无效可切换检索方式。带副作用的请求超时后，先查执行状态或依靠幂等标识，避免重复操作。

**练习：** 分别设计搜索无结果、HTTP 429、写操作超时三种故障的处理流程。
:::

### Q7：不同渠道的证据互相矛盾，应该如何取舍？

考察点：来源、时效、适用范围、冲突保留。

::: details 展开学习版参考答案与练习
先确认是否在讨论同一个对象、时间和定义，再比较来源可靠性、版本及适用范围。不要简单设定「网页永远低于内部文档」：过期的内部文档也可能不适用，转载数量多也不意味着独立证据多。

保存冲突双方的原文位置与时间，说明采用哪条证据及理由。无法消解时应给出条件化结论或请求人工判断。原帖使用了医疗资料冲突的情境；这类高风险判断不能仅靠通用来源排序自动下结论。

**练习：** 一份旧版操作手册与一份新版官方公告冲突。写出核对版本、确认适用对象和保留引用的步骤。
:::

### Q8：召回大量网页后，怎样选择送给模型的内容？

考察点：召回、重排、去重、上下文组装。

::: details 展开学习版参考答案与练习
先过滤不可访问、不适用或无权限的内容，再去除同源转载；按与问题的相关程度重排，并根据子问题覆盖度和时效挑选证据。在 Token 预算内保留不同方面的信息，避免排名靠前的几段都在说同一件事。

保留标题、来源链接、时间和原文位置，方便生成引用。评估时分开检查「需要的证据有没有召回」「有没有被重排保留」「最终答案有没有忠实使用」，不要把全部问题都归因于模型。[本站检索优化课程](/rag/b3-hybrid-search-rerank)

**练习：** 收集十条结果，其中包含重复转载和旧版本。选三条进入上下文，并写出淘汰理由。
:::

## 三、项目链路与工具设计

本组 Q9–Q12 来源：[在抱佛脚的芝士很完美的美团 Agent 一面](https://www.nowcoder.com/feed/main/detail/18fa4134edb14e8c901787ee5cd33ace)。

### Q9：用一个具体任务，解释输入如何变成最终结果。

考察点：端到端链路、本人职责、可验证产出。

::: details 展开学习版参考答案与练习
用一个真实且脱敏的案例串起来：输入和权限校验 → 识别意图与补齐参数 → 检索或任务规划 → 调用工具 → 验证结果 → 输出或人工确认。解释每一步的输入、输出、状态存放位置和失败出口。

例如订单查询助手：用户提供订单标识，服务端验证查询权限，工具查询订单及退款状态，模型据结果解释进度。模型不能直接凭聊天内容确认身份，也不能把「已生成退款建议」当成「退款已完成」。项目效果要提供测量口径，区分实际数据与设计预期。

**练习：** 画出自己项目的一条成功链路，再补画一条工具超时链路，标出你实际开发的部分。
:::

### Q10：为什么采用固定工作流？换成自主决策有什么取舍？

考察点：确定性、灵活性、验证成本。

::: details 展开学习版参考答案与练习
路径稳定、合规步骤明确的业务，适合把顺序和约束写进工作流；未知步骤多、需要探索的任务，可以让模型根据反馈选择下一步。两者可以组合：外围用工作流约束权限和审批，内部局部使用自主决策。[Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/research/building-effective-agents)

选型时对比任务成功率、延迟、成本和排障难度，而不是认为自主程度越高越好。例如退款审批的必经校验不应由模型自由跳过，但解释复杂失败原因可以采用多轮检索。

**练习：** 将「查订单、分析原因、提交退款申请」三个阶段分别分配给确定逻辑或模型，并解释边界。
:::

### Q11：输入不足以确定操作对象时，系统怎样继续处理？

考察点：参数校验、歧义消解、人工确认。

::: details 展开学习版参考答案与练习
先按工具契约识别缺失字段，区分可从已授权上下文读取的值和必须由用户指定的值。如果有多个候选对象，就展示可区分的信息让用户选择，不能把相似度最高的对象当作用户授权。

执行前重新校验身份、权限、资源版本和必要参数；会产生副作用的操作，应让用户确认具体对象与动作。工具层也要验证参数，不能因为模型输出符合 JSON 格式就默认其业务含义正确。

**练习：** 用户说「把昨天那单取消掉」，但查到三笔订单。写出最短的澄清问题，以及执行前必须验证的字段。
:::

### Q12：Skills、MCP、Function Calling、Workflow 和子 Agent 怎样配合？

考察点：协议、调用、流程与职责的分层。

::: details 展开学习版参考答案与练习
这些概念所在层次不同，具体产品中的 Skills 形式也可能不同：

| 概念 | 本文采用的含义 |
| --- | --- |
| Skill | 可复用的任务说明及配套资源，可能包含脚本 |
| MCP | 应用与工具、资源等能力提供方之间的上下文交换协议 |
| Function Calling | 模型生成结构化工具调用请求，由应用校验、执行并回传结果 |
| Workflow | 由代码或图定义步骤、条件分支和执行约束 |
| 子 Agent | 被委派子任务、具有自身执行过程的工作单元 |

例如：工作流确定审核步骤，Skill 描述审核方法，模型选择查询工具，应用通过 MCP 客户端访问服务；独立的材料整理任务可以交给子 Agent。MCP 不规定模型怎样推理，也不会替你完成业务权限设计。[MCP 官方架构](https://modelcontextprotocol.io/docs/learn/architecture)

**练习：** 给自己的架构图标注这五个概念，没有使用的部分直接写「未使用」，说明原因。
:::

## 四、平台化与工程交付

本组 Q13–Q16 来源：[赛文X的蚂蚁 Agent 开发二面](https://www.nowcoder.com/feed/main/detail/beae35cec366487a918abee5421216f2)。

### Q13：团队内部的提效 Agent，怎样推广成公司通用能力？

考察点：可复用边界、多租户、运营成本。

::: details 展开学习版参考答案与练习
先验证多个团队是否确实有共同需求，再提取工具接入、身份认证、任务状态、日志追踪、费用统计和评测等共性能力。保留业务规则、权限和知识来源的差异，不要把单团队的默认假设硬编码成全公司的规则。

推广时要处理租户隔离、配额、版本升级、审计和故障归属。选择第二个差异明显的场景试接入，记录接入工时、额外定制量和维护成本，才能判断是否值得平台化。

**练习：** 比较研发助手与客服助手，列出三个共性能力和三个必须隔离的业务规则。
:::

### Q14：从理解需求到上线验收，自动交付容易在哪里失败？

考察点：验收标准、环境、验证闭环。

::: details 展开学习版参考答案与练习
常见断点包括需求理解错误、修改范围失控、测试没有覆盖真实场景，以及部署成功但业务结果不正确。应先约定可观察的验收标准，再让实现和验证围绕它展开。

保存需求与变更的对应关系，审查补丁，运行相关检查，在隔离环境验证后逐步发布。最终通过服务健康和业务指标确认效果，必要环节由人审核。不能让生成代码的模型仅凭自己的描述宣布交付成功。

**练习：** 为「新增按订单状态筛选」写出三条验收标准，以及代码通过测试但仍不应发布的一种情形。
:::

### Q15：怎样设置自动回滚的判断条件？

考察点：指标、基线、补偿与熔断。

::: details 展开学习版参考答案与练习
把技术指标与业务指标同时纳入判断，例如错误率、延迟、任务成功率及错误写入事件。阈值要基于业务基线、观察窗口和最低样本量设计；严重越权等事件可直接触发停止操作。不要给所有项目套同一套百分比。

区分停止 Agent、回退模型或提示词版本、回退代码部署，以及补偿外部操作。撤回部署不会自动撤销已经发送的消息或写入的数据。回滚前还要考虑数据库兼容性，避免反复自动切换造成更大故障。

**练习：** Agent 已发出一封错误邮件。说明回退程序能解决什么、不能解决什么，以及后续如何补偿。
:::

### Q16：怎样用对照实验判断 Agent 是否带来改进？

考察点：实验单元、指标定义、统计与成本。

::: details 展开学习版参考答案与练习
先明确改进目标，例如降低人工处理时间，同时不增加错误操作。离线使用保留测试集比较版本，再对符合条件的用户或任务随机分组。分组单元应匹配业务，避免同一用户或共享记忆在两组之间造成干扰。

提前规定主指标、护栏指标、观察周期和样本量，检查实际分流是否异常；结合置信区间与业务收益判断，不因一天的数据好看就停止实验。把模型费用、人工复核和失败重做成本一并计入，防止速度提升却总成本上升。

**练习：** 为工单处理 Agent 设计一个主指标、两个护栏指标和一种可能污染实验的情况。进一步阅读：[Microsoft 实验平台文章索引](https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/)。
:::
