# Chunking 策略全解

进阶专题 B1 · 关联：第二课「摄入流水线」里的 [chunkText 切块](/rag/02-ingestion-pipeline)

::: tip 本专题定位
你已经见过本仓库的 `chunkText`（按标题 + 中文标点切，800 字符）。这一课跳出单个实现，系统讲 **chunking 为什么难、有哪些策略、怎么选**，并回看本仓库的选择。
:::

## 为什么 chunking 是 RAG 质量的基石

一句话：**检索出来的内容质量 ≈ chunk 的质量**。chunking 决定了：

- **粒度**：太粗 → chunk 里夹杂无关内容，检索"看似相似实则偏题"；太细 → 语义被切断，上下文不完整
- **语义完整性**：一句话、一段论证被劈成两半，embedding 的向量就不准，LLM 拿到的上下文也是残缺的
- **成本**：chunk 越多 → embedding 调用越多、向量库越大、检索越慢

RAGHub 的 FAQ 里，第一个常见问题"Poor retrieval quality"给出的第一个解决方案就是 **Optimize chunking strategy and embeddings**。

## 主流的 chunking 策略

### 1. 固定长度切分（Fixed-size）

最简单：按字符数或 token 数硬切，可选**重叠（overlap）**。

```text
原文: A B C D E F G H I J K L M N
chunk1: [A B C D E]   chunk2: [D E F G H]   chunk3: [H I J K L] ...
        └──重叠 2 个──┘        └──重叠 2 个──┘
```

- ✅ 实现零成本，快
- ❌ 完全不理解语义，可能从句子中间切断
- **适用**：内容结构简单、对效果要求不高的场景

### 2. 递归字符切分（Recursive Character Splitting）

LangChain 的招牌策略：**按"分隔符优先级列表"递归切**，优先在语义损失最小的地方切。

```text
切分优先级（由强到弱）：
  1. 段落分隔（\n\n）
  2. 换行（\n）
  3. 句号/句末标点（. ！？）
  4. 空格/逗号
  5. 字符

先尝试按 \n\n 切 → 某块还超长 → 按 \n 切 → 还超长 → 按句子切……
```

- ✅ 相比固定切分，句子/段落完整度大幅提升
- ✅ 可配置分隔符列表，中文可把 `。！？；` 加进优先级
- ❌ 仍是"基于规则"，不理解语义
- **适用**：通用场景的首选，本仓库 `chunkText` 就是这个思路的简化版（标题 + 中文标点）

### 3. 语义切分（Semantic / Embedding-based）

用 embedding 判断句子之间的**语义跳跃点**：相邻两句的向量相似度骤降处就是切分点。

```text
句子向量相似度:  S1—S2: 0.91  S2—S3: 0.89  S3—S4: 0.31  ← 语义跳跃！
切分点:           [S1 S2 S3]  [S4 S5 ...]
```

- ✅ 切出的块语义最连贯
- ❌ 慢（每句都要 embedding）、贵
- **适用**：对效果要求高、内容杂（如长文档混排）的场景

### 4. 结构化切分（Structure-aware）

**先按文档天然结构切**（Markdown 标题、HTML 标签、PDF 章节、表格、代码块），再在结构块内做二次切分。

```text
Markdown 文档:
  ## 介绍         → chunk1（标题+引言）
  ### 用法         → chunk2
  | 表格...        → chunk3（表格单独保留，别拆散）
```

- ✅ 语义边界最自然，尤其适合**技术文档/博客**（本仓库用的就是这种）
- ✅ 还能把标题作为 chunk 的一部分，检索时"带上标题"上下文更好
- ❌ 依赖文档格式，非结构化文本（聊天记录等）用不上
- **适用**：Markdown/HTML/PDF 为主的场景，如本仓库的 Hugo 博客

### 5. 父子切分（Parent-Child / Small-to-Big）

**小 chunk 用于检索，大 chunk（父块）用于给 LLM 生成**——两者结合。

```text
检索用: [小块A1] [小块A2] [小块B1]   ← 小块，检索精准
生成用:         [大块A(含A1,A2)]      ← 命中 A1 时，把整个大块 A 给 LLM
```

- ✅ 兼顾"检索精准"和"上下文完整"
- ❌ 索引要存两层，实现复杂些
- **适用**：QA 场景，用户问题短而文档段落长

## chunk 大小怎么选

没有绝对标准，但有经验区间和权衡：

| 因素 | 影响 |
| ---- | ---- |
| **embedding 模型上限** | 硬约束，chunk 必须小于模型最大输入（如 512/2048 token） |
| **LLM 上下文窗口** | 塞进提示词的 chunk 总和要远小于窗口，留出对话和回答空间 |
| **内容密度** | 代码/术语密集 → 偏小；叙述性长文 → 可偏大 |
| **中文特殊性** | 1 token ≈ 0.6~1 个汉字（不同模型不同），中文通常按"字符数"切更直观 |

本仓库的选择：`maxLen = 800`（字符），入库时 text 再截到 500——在"足够语义完整"和"不撑爆上下文"之间取的折中。

## 回看本仓库的 chunkText

对照上面的框架，`chunkText` 属于 **结构化 + 递归字符的混合**：

1. **按标题切**（`/^#{1,6}\s+/m`）→ 结构化切分的核心
2. **长块按中文标点保句切**（`/(?<=[。！？!?；;]\s*)/` 后行断言）→ 递归字符策略的"句子优先级"

这正是一个**中文技术博客**的最优解：标题天然分主题、中文没有空格、按标点保句最不破坏语义。如果你要给**别的类型内容**做 chunking，先问：它有没有结构？句子边界清楚吗？需要多高的检索精准度？

## 自测

::: details 测验 · 点击展开

**1. 固定长度切分最大的缺点是？**
- ❌ 实现太复杂（它是最简单的）
- ✅ **可能在句子中间切断，破坏语义**（不理解内容结构）
- ❌ 成本太高（它成本最低）
- ❌ 需要 embedding 模型（不需要）

**2. LangChain 递归字符切分的核心思想是？**
- ❌ 每个字符都单独成块
- ✅ **按分隔符优先级递归切，优先在语义损失最小处切**（段落→换行→句子→空格→字符）
- ❌ 用 embedding 找语义跳跃点（那是语义切分）
- ❌ 先转成 HTML 再按标签切（那是结构化切分）

**3. 父子切分（Parent-Child）的核心思路是？**
- ❌ 所有 chunk 一样大
- ✅ **小 chunk 检索、大块（父块）生成**，兼顾精准与完整
- ❌ 只检索不生成
- ❌ 把所有内容合成一个超大块

**4. 本仓库 chunkText 属于哪种策略？**
- ❌ 纯固定长度切分
- ✅ **结构化（按标题）+ 递归字符（按中文标点）的混合**
- ❌ 纯语义切分（没有用 embedding 找切点）
- ❌ 父子切分（没有两层索引）

**5. 中文 chunking 相比英文，最需要额外处理的是？**
- ❌ 中文没有词形变化
- ❌ 中文 chunk 必须更小
- ✅ **中文没有空格分词，要靠句读标点（。！？；）保句切分**
- ❌ 中文不需要切分

:::

## 小结

| 策略 | 优点 | 缺点 | 适合 |
| ---- | ---- | ---- | ---- |
| 固定长度 | 简单快 | 切碎语义 | 原型/简单内容 |
| 递归字符 | 句子完整 | 不懂语义 | 通用首选 |
| 语义切分 | 语义连贯 | 慢贵 | 杂长文档 |
| 结构化 | 边界自然 | 依赖格式 | 技术文档/博客 |
| 父子切分 | 精准+完整 | 实现复杂 | 短问长答 QA |
