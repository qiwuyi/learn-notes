# RAG 评估

进阶专题 B4

::: tip 本专题定位
前面几课教你"怎么做 RAG"，这一课讲**怎么知道做得好不好**。RAG 的效果不能靠"感觉"，要用指标量化——这一课介绍主流的评估框架（ragas 等）和核心指标。
:::

## 为什么要评估

RAG 系统有两个独立环节，坏可能坏在不同地方：

```text
问题 ──▶ [检索] ──▶ 相关文档 ──▶ [生成] ──▶ 回答
            ▲                         ▲
        检索准不准？               回答对不对？
    （检索不到/检索偏了）      （答非所问/编造/漏要点）
```

如果回答不好，你得知道是**检索的锅**还是**生成的锅**，才能对症下药。评估框架就是给你一套可量化的指标来定位问题。

## 核心指标（以 ragas 为例）

业界最常用的评估框架是 **ragas**（RAG Assessment），它把 RAG 质量拆成几个可测的维度。核心四件套：

| 指标 | 英文 | 衡量什么 | 查的是哪个环节 |
| ---- | ---- | -------- | -------------- |
| **忠实度** | Faithfulness | 回答是否**忠于检索到的上下文**，有没有编造（幻觉） | 生成 |
| **答案相关性** | Answer Relevancy | 回答是否**切题**，有没有答非所问、废话 | 生成 |
| **上下文相关性** | Context Relevancy | 检索到的上下文是否**相关**（含金量） | 检索 |
| **上下文召回率** | Context Recall | 需要的答案信息是否**都被检索到了** | 检索 |

其中最关键、最容易出问题的是 **Faithfulness（忠实度）**——它是"幻觉"的直接度量：回答里的每个论断，能不能在检索到的上下文里找到依据。找不到依据的论断越多，忠实度越低。

```text
问题：Kubernetes 里什么是 Pod？
上下文：[Pod 是 K8s 最小部署单元...]
回答A：Pod 是最小部署单元。           → 忠实（有依据）
回答B：Pod 是最小部署单元，也是调度器。→ 部分忠实（"调度器"上下文没提，可能幻觉）
```

## 其他常用指标

- **检索类**：Recall@k、Precision@k、MRR（排序质量，离线标注可用）
- **RAGAS 扩展**：
  - **Context Precision**：相关上下文排得够不够靠前
  - **Noise Sensitivity / Context Utilization**：上下文里的噪声有没有影响回答
- **实用层面**：答案被采纳率、用户追问率、Token 成本/延迟

## 评估的两条路线

### 1. 基于 LLM 的评估（主流，如 ragas）

**让另一个 LLM 当"裁判"**，给它（问题、检索上下文、模型回答），让它打分/判论断是否有依据。

```text
裁判 LLM 输入：
  问题：...
  上下文：...
  回答：...
→ 输出：忠实度 0.87，答案相关性 0.91，...
```

- ✅ 不用人工标注、可大规模、贴近真实问答
- ❌ 裁判 LLM 本身有偏差、有成本、有延迟
- **注意**：裁判模型最好和被评模型**不同**（避免"自己评自己"偏袒）

### 2. 人工 / 规则评估

- **Golden Set（金标集）**：人工准备一批 (问题, 期望回答, 期望来源) 的标准集，定期回归
- **规则检查**：回答是否包含来源、是否为空、长度是否合理
- **用户反馈**：生产环境的点赞/点踩、追问率

最佳实践是**两者结合**：LLM 评估做持续回归，Golden Set 保底线，用户反馈抓生产。

## 评估流程建议

```text
1. 建测试集（20~100 条典型问题，覆盖各种难度/主题）
2. 跑一轮 RAG，收集（问题, 上下文, 回答）
3. 用 ragas 算四件套指标
4. 看短板：忠实度低 → 生成/提示词问题；上下文相关性低 → 检索/切块问题
5. 改一处 → 重跑 → 对比指标 → 迭代
```

::: warning 常见误区
- ❌ 只看"回答像不像人话"——不量化就无法迭代
- ❌ 只测 3 条样例——没有统计意义
- ❌ 改动后不回归——改 chunk 可能悄悄弄坏别的问题
:::

## 和本仓库的对照

本仓库没有内置评估（tests/ 里有 ingest/retriever 的单元与集成测试，但那是**代码正确性**测试，不是**RAG 质量**评估）。要给它加质量评估，可以在仓库外建一个评估脚本：

```text
用 ragas + 一批测试问题，调 /chat 接口拿回答，
算忠实度/上下文相关性等指标，量化每次改动的效果。
```

## 自测

::: details 测验 · 点击展开

**1. Faithfulness（忠实度）衡量的是？**
- ❌ 回答是否漂亮
- ✅ **回答是否忠于检索到的上下文，有没有编造**（幻觉的直接度量）
- ❌ 检索到了多少文档
- ❌ 回答快不快

**2. "Context Relevancy"低，说明问题可能出在哪？**
- ❌ 生成环节（它衡量的是检索到的上下文是否相关）
- ✅ **检索/切块环节**（检索到的内容本身不相关）
- ❌ LLM 太弱
- ❌ 提示词太长

**3. ragas 这类 LLM 评估的本质是？**
- ❌ 人工逐条打分
- ✅ **用另一个 LLM 当裁判，对回答/上下文打分**（可规模化）
- ❌ 用数学公式算精确值
- ❌ 纯靠规则匹配

**4. 用 LLM 评估时，一个重要的注意事项是？**
- ❌ 必须用最强的模型
- ✅ **裁判模型最好和被评模型不同**（避免"自己评自己"偏袒）
- ❌ 只能评英文
- ❌ 不需要测试集

**5. 回答质量下降，正确的排查思路是？**
- ❌ 直接换更大的 LLM
- ✅ **先看指标定位环节**：忠实度低看生成，上下文相关性低看检索
- ❌ 直接加 Rerank
- ❌ 放弃评估凭感觉调

:::

## 小结

- RAG 效果要**量化**，不能凭感觉
- 核心四件套：**忠实度 / 答案相关性 / 上下文相关性 / 上下文召回率**（ragas）
- 两条路线：**LLM 评估（规模化）+ Golden Set/用户反馈（保底线）**
- 指标帮你**定位是检索的锅还是生成的锅**
